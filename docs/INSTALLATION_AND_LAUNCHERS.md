# Installation and launchers

The emulator is not considered usable merely because a binary exists. Installation must leave clear, durable ways to start each intended program.

## AS2K stable

The stable installation must provide:

1. an application-menu entry named **AS2K Emulator**;
2. a stable command named `as2k` available through the normal executable search path;
3. an optional desktop shortcut generated by the installer or setup command when requested;
4. an icon and descriptive metadata suitable for the desktop environment;
5. a launcher that targets the installed stable executable, not a build directory, worktree or temporary path;
6. startup without requiring the terminal to be positioned in the repository;
7. access to the mouse-driven ROM/DictROM selector when no compatible image has been configured.

The menu launcher and command must open the same stable application and use the same stable configuration location.

## `as2k-diag`

The private diagnostic variant is not installed system-wide. Its private repository must provide a clearly named executable launcher, provisionally `run-as2k-diag`, that:

- resolves its paths relative to the private repository rather than the caller's current directory;
- selects the diagnostic binary and diagnostic configuration explicitly;
- keeps diagnostic NVRAM, state, logs and captures separate from stable;
- exposes a deterministic entrypoint for Commander;
- prints or reports that the diagnostic variant is active;
- fails with a clear instruction when the diagnostic binary has not been built.

A project-local desktop file may be provided for development convenience, but it must remain private and must not masquerade as the installed stable application.

## Path and privacy rules

Launchers must not:

- contain ROM, DictROM, NVRAM or saved-state data;
- embed credentials or private machine tokens;
- point to disposable build-numbered directories;
- silently fall back from stable to diagnostic or vice versa;
- share mutable configuration/state locations between variants.

User-selected image paths may be stored in the appropriate local configuration, which remains outside Git.

## Acceptance tests

Launcher acceptance requires proving:

- the stable menu entry starts the installed stable executable;
- `as2k` works from an arbitrary directory;
- the optional stable desktop shortcut resolves correctly;
- `run-as2k-diag` works from an arbitrary directory without installation;
- Commander starts exactly `as2k-diag`;
- both variants report their identity;
- stable and diagnostic configurations, NVRAM, states and logs remain isolated;
- uninstalling or replacing the stable build does not damage the private diagnostic working tree.


## Prepared Linux implementation

The R0 preparation branch now provides:

- `packaging/as2k-launcher.sh` — installed stable launcher with isolated XDG paths;
- `packaging/as2k.desktop.in` — application-menu template;
- `scripts/install-stable.sh` — install a validated reduced binary under a prefix;
- `scripts/uninstall-stable.sh` — remove program/menu files without deleting user data;
- `scripts/validate-stable-static.sh` — fail-closed static gate for fixed-ROM leakage and packaging syntax;
- `docs/STABLE_INSTALL_LAYOUT.md` — exact system/user path contract.

These files are preparation artifacts until the reduced native binary is compiled and validated on T160. They do not authorize installing an unvalidated build.
